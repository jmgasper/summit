# Handoff: coordinated graphics rendering fixes (September 22, 2026)

Written so another agent can take over mid-stream. Everything below is verified
on the workstation unless it says otherwise.

## The goal

Performance work on Summit, in three parts (the original `/goal`):

1. **Render and scrolling performance.** Scrolling a content-heavy page must not
   be choppy on a machine this size; use OpenGL where it is available, keep the
   software path working.
2. **NVDEC media playback** on sites like youtube.com. *Not started in this
   round.*
3. **Speedometer 3.1** -- beat Firefox, by using Haiku's threads properly.

The immediate task was: *"Please fix the requestAnimationFrame issue and the
wrong thread bug so we can get an idea of where we're at with performance."*
Both are fixed. Two further bugs were found and fixed on the way, and one new
problem was found and is **not** fixed.

## Where it stands in one line

Scrolling in the coordinated-graphics + Skia build is **62.3 fps with zero
frames over 33 ms** (was 44.4 fps on the app_server backend, 7.7 fps on the
first Skia build). Speedometer 3.1 is **2.1x faster per suite** where it
completes, but the full benchmark still hangs partway, for at least two
different reasons -- one identified, one not.

## What was fixed

All of these are working-tree changes in `.cache/WebKit`, already folded into
`engine/patches/0001-haiku-port.patch` by `tools/update-engine-patch.py`.

1. **`RunLoopObserver` ignored the run loop it was given.**
   `Source/WebCore/platform/RunLoopObserver.{h,cpp}`.
   `ThreadedCompositor::renderLayerTree()` schedules its did-composite observer
   with `schedule(&RunLoop::mainSingleton())` *from the compositor thread*. The
   Haiku implementation used `RunLoop::currentSingleton()`, so the callback ran
   on the compositor thread -- and with it `didComposite`, `updateRendering`,
   the whole rendering update, and every `WebCore::Timer` it starts. Those
   timers land in the compositor thread's `ThreadTimers` heap, which nothing
   services, so the third rendering update wedged the page for good. This was
   the "requestAnimationFrame issue".
   - `PlatformRunLoop` is now `RunLoop*` on Haiku and `schedule()` honours it.
   - A bool under a lock answers `isScheduled()`, not the timer pointer: the
     timer can fire on the target thread before `dispatchAfter()` returns.
   - Cross-thread scheduling uses `RunLoop::dispatch()`, not a timer.
     `RunLoop::TimerBase::start()` takes the target `BLooper`'s lock, which the
     target thread holds while dispatching -- including while it waits on the
     thread doing the arming.

2. **Image decodes finished on the wrong thread.**
   `Source/WebCore/platform/graphics/AsyncImageDecoder.cpp`. The reply run loop
   is `RunLoop::currentSingleton()` only when the request came from the main
   thread, `RunLoop::mainSingleton()` otherwise. A decode requested from a Skia
   paint used to complete on that worker and hit
   `RELEASE_ASSERT(isMainThread())` in `MemoryCache::singleton()`.
   Verified: `en.wikipedia.org` now loads, lays out and draws with the web
   process intact.

3. **Render buffers were never returned to the swap chain.**
   `Source/WebKit/UIProcess/haiku/AcceleratedBackingStore.{h,cpp}`. The UI
   process must answer `AcceleratedSurface::ReleaseBuffer`; it only answered
   `FrameDone`. `SwapChain::nextTarget()` therefore allocated a new
   `ShareableBitmap` (two file descriptors) per frame until the web process died
   with "Failed to create handle for shared memory buffer". `presentBitmapHaiku`
   copies the pixels before returning, so the buffer is released right after the
   present.

4. **A dropped wake-up could suspend dispatch permanently.**
   `Source/WTF/wtf/haiku/RunLoopHaiku.cpp`. `RunLoop::wakeUp()` ignored the
   result of `PostMessage('loop')`. That message is what lets `performWork()`
   lift `suspendFunctionDispatchForCurrentCycle()`, and nothing posts again to a
   queue that is already non-empty, so one dropped wake-up stops every
   `RunLoop::dispatch()` in the process. It now retries from the timer thread
   (`TimerScheduler::scheduleWakeUp`), as dropped timer notifications already
   did. Retrying inline would deadlock when the caller is the looper itself.

5. **New switch: `SUMMIT_DISABLE_ASYNC_SCROLLING=1`.**
   `Source/WebKit/WebProcess/WebPage/CoordinatedGraphics/DrawingAreaCoordinatedGraphicsGLib.cpp`.
   Upstream's `WEBKIT_DISABLE_ASYNC_SCROLLING` is behind
   `ENABLE(DEVELOPER_MODE)`, which release builds do not set. This is the
   equivalent for Summit and is how the scrolling thread was ruled in as the
   cause of one hang.

6. **Two harness bugs** (`tools/bench/`), both of which corrupted measurements:
   - `guest.wake_display()` built its kill command with `awk "{print $2}"`
     inside a single-quoted Python string, so the remote login shell ate `$2` and
     the screen blanker was never killed. A blanked screen stops app_server
     drawing and the browser looks frozen -- three scroll runs were recorded as
     "timeout" for this reason alone.
   - `run-probe.py` woke the display once, before the run; it now does so every
     30 s, because the blanker returns on every idle period.

## The open problem

Speedometer 3.1 does not finish in the coordinated build.

**Hang A -- the scrolling thread.** `Editor-CodeMirror` hangs at the same step
with async scrolling on and completes with `SUMMIT_DISABLE_ASYNC_SCROLLING=1`.
The suite has a "Scroll" step. Not diagnosed further; the scrolling tree commit
or its reply is the place to look (`ThreadedScrollingTree`,
`ThreadedScrollingCoordinator`, `ENABLE(SCROLLING_THREAD)` paths in
`LayerTreeHost::requestComposition`).

**Hang B -- something else.** With async scrolling disabled, the full
10-iteration run still hangs, at `TodoMVC-Lit-Complex-DOM` step 35/580, with the
benchmark's iframe blank. One-iteration runs pass that same suite, so it is not
a fixed step; it looks intermittent or time-dependent.

What the watchdog established about the hangs (instrumentation has since been
removed -- see "How to get it back"):

    Summit stall: 3.4 s with no rendering update; waitingForRenderer=0
      scheduledWhileWaiting=0 frozen=0 suspended=0 observerScheduled=0 updating=0
      | state=Idle reasons=0 waitingForTiles=no renderTimerActive=no
        didCompositeFn=none pendingTiles=no suspended=0
    Summit stall: page | pageScheduled=no remainingSteps=0 unfulfilled=0
      visible=yes throttling=0 updateInterval=15 rafDocuments=0 activityState=31
      timerThrottling=0 timerAlignmentMs=0 | schedulerScheduled=no
      refreshTimer=none timerActive=no monitorScheduled=no useTimer=no
    Summit stall: loop | dispatchSuspended=0 hasSuspended=0 currentQueue=0
      nextQueue=0 | timers heap=7 frontMs=1098.6 firing=no sharedTimer=set
      pendingFireMs=1098.6

Read that as: **the rendering pipeline is not what is stuck.** The compositor is
idle with nothing pending, no document has a `requestAnimationFrame` callback
waiting, nothing has asked for a rendering update, dispatch is not suspended and
its queues are empty, DOM timer throttling is off, and the timer heap's next
entry is legitimately about a second away. The page is waiting on something in
its own JavaScript -- a promise or a poll -- that never completes. The next step
is to find out *what* the page is waiting for, not to keep instrumenting the
engine: the Web Inspector, or a build of Speedometer with progress beacons
(`run-speedometer.py --progress-beacons`), would say directly.

## How to get the instrumentation back

It was all removed before committing. It was, in order of usefulness:

- A repeating 1 s `RunLoop::Timer` in `LayerTreeHost::updateRendering()` that
  logs when more than 3 s pass with no rendering update, dumping the layer tree
  host's flags plus `ThreadedCompositor`, `Page`, `RenderingUpdateScheduler`,
  `RunLoop` and `ThreadTimers` state. Each of those classes got a temporary
  `summitStateDescription()`.
- Gap logging in `LayerTreeHost::updateRendering()`,
  `requestCompositionForRenderingUpdate()` and
  `RenderingUpdateScheduler::displayRefreshFired()` for intervals over 100 ms.
- `isMainThread()` in `RenderingUpdateScheduler::startTimer()` plus
  `WTFReportBacktrace()` when `scheduleRenderingUpdate()` is off the main
  thread. **This is the one that found bug 1** and is the first thing to reach
  for if a page freezes again.

Note that touching `ThreadTimers.h` or `RunLoop.h` costs a ~1300-target rebuild;
adding the logging to `.cpp` files only costs a handful.

## Workstation gotchas that cost time

- **`ps` truncates the team name**, so `grep WebProcess` misses the web process
  (it shows as `WebProce`). Twice I concluded the process had died when it had
  not. Use `grep '[W]ebProce'`.
- **The screen blanker returns every idle period** and a blanked screen makes
  the browser look frozen. A guard loop is running on the workstation
  (`/boot/home/no-blank.sh`); it has been stopped again, so start it with
  `nohup /boot/home/no-blank.sh &` before a long benchmark and kill it after.
- **`Debugger --save-report --team N`** produces a report with no stack traces
  for a hung (as opposed to crashed) team, and the harness then counts that
  report as a crash. One run was recorded as `crash-detected` because of my own
  diagnostic. `Debugger --cli --thread N` needs no other debugger attached and
  wants `thread <id>` before `bt`.
- Summit is `B_SINGLE_LAUNCH` per executable path: a second launch of the same
  bundle only adds a tab, and the harness refuses to start.
